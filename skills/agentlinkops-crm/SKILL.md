**The local surface is the ledger file, not this CRM.** `.agentlinkops/links.jsonl` in the user's repository (or a `.linktrail/` directory from an earlier install, read until `agentlinkops migrate` renames it) declares the links they expect, want and have earned, and `agentlinkops check` runs the exact cloud verifier against it without an account. Run the CLI as `node cli/agentlinkops.mjs` from the repository or plugin-package root (`cli/linktrail.mjs` still works and prints a one-line notice); the packaged plugin ships the CLI, its pinned verifier modules and their one dependency (parse5, MIT) inside the package, so `check` runs with no npm install and no network. It needs Node 22 or newer (`adopt` reads SQLite databases through `node:sqlite`); the Python helper below needs Python 3.10+. This CRM is one optional adapter beside CSV and JSONL: it is available, tested and unchanged, and nothing requires it. When a user already keeps links here, `agentlinkops adopt <db>` reads it into ledger entries — read-only, adding no schema — and previews unless `--write` is given. Do not propose the CRM as the place a user should start keeping links; propose it when they want contacts and outreach activity beside them, or when they already have one.

To record a link in the ledger: `agentlinkops add --source URL --target URL --intent expected [--anchor TEXT] [--ref ID] [--note TEXT]` (`--intent wanted` for a link not yet earned; `agentlinkops init` first in a repository without `.agentlinkops/`). `agentlinkops check` then verifies every expected link and exits 0 when all are present, 1 when one is observed absent with complete evidence, 2 on a usage or ledger error; an unknown never fails.

Use the deterministic Python helper at `../../scripts/agentlinkops.py`, resolved relative to this skill's directory. It requires Python 3.10+ and only its standard library. Run `--help` for the command surface. Keep the database outside the plugin installation directory; updates can replace that directory.

Read [the CLI contract](../../references/cli.md) for fields and examples. The CRM contains products, campaigns, contacts, opportunities, activities and placements. Use explicit stable IDs and upsert a record to update it. Bulk records of one entity are committed together. Save source URLs and observed dates alongside contact and qualification evidence.

When the user asks to manage a disavow list, read [the disavow contract](../../references/disavow.md). Scope every operation to the exact user-selected URL-prefix property. Preserve provenance and the user's explicit rule choices. Do not decide to disavow a site from a low score, inaccessible page or generic risk label. The helper imports and exports local files; it has no Google upload capability. Reimporting a prior file does not reactivate rules the user disabled.

For a shareable placement report, read [the report contract](../../references/reports.md). Select the requested project and brand/title. Reports include observed placement data by default. Include local notes or cost amounts only when the user requests that content; those fields may contain private commercial context. The output is self-contained HTML, not a generated PDF. A report timestamp does not make its underlying observations fresh.

Preserve an existing CRM's workspace binding. Never initialize over an unrelated database, rewrite migration checksums, delete data to resolve a migration error, or reset a sync cursor to hide an expired feed. The helper backs up existing databases before applying new migrations.

Track outreach through `external_message_id`, activity kind, time and outcome. Keep email bodies and mailbox credentials in the user's existing email system. Local notes are not a secret store. CSV export neutralizes spreadsheet formula prefixes; JSON is the lossless interchange format.

For ledger cloud setup, follow [Connect the ledger CLI](../../references/cli.md#connect-the-ledger-cli-to-an-existing-project): create a scoped credential in the workspace, supply it through the process environment, verify the existing project with `connect`, then review `sync --dry-run`. An explicit ledger-ID selection keeps unrelated local records out of uploads. MCP OAuth credentials stay in the MCP client.

For recurring cloud changes, use the host's already connected AgentLinkOps tools when available. The standalone `sync` helper requires `AGENTLINKOPS_API_URL` and `AGENTLINKOPS_API_KEY` in its process environment (the `LINKTRAIL_` spellings are still accepted with a warning during the pilot compatibility window). Never request a key in chat or place it in command arguments, source files or CRM notes. Account connection and permissions are separate from local CRM utility. Explain unavailable access neutrally and preserve completed local work.

Sync updates `cloud_state` on placements and preserves local status, notes and opportunity relationships. A fetch failure is not proof that a backlink disappeared. Keep `unknown`, `suspected_missing` and confirmed outcomes distinct. Read the new events and decide what action, if any, the user's agent should take; receipt of an event does not authorize sending an email.
